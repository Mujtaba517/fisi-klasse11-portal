Daten systemübergreifend bereitstellen · 96 Std.

🎯 هدف Lehrplan

داده را از منابع غیرمتمرکز جمع کن، آماده کن و برای استفاده بعدی در اختیار بگذار.

تحلیل منبع (ساختار، دسترسی، حقوق)، انتخاب منابع ناهمگون، طراحی با امنیت اطلاعات، پیاده‌سازی تیمی، تحویل با مستند کاربری.

🧩 انواع Datenquellen

  • پایگاه رابطه‌ای (MySQL, PostgreSQL, SQL Server)
  • فایل: CSV, JSON, XML, Excel
  • API: REST (JSON) / گاهی SOAP
  • سیستم سازمانی: ERP, CRM, Ticket
  • IoT / سنسورها

قبل از اتصال بپرس: داده شخصی هست؟ مجوز داری؟ پروتکل دسترسی چیست؟ نرخ به‌روزرسانی چقدر است؟

🗃️ مدل‌سازی و SQL

  • ER-Modell – موجودیت، ویژگی، رابطه
  • Primary Key / Foreign Key
  • SELECT … JOIN … WHERE برای ترکیب جداول
  • نرمال‌سازی پایه برای کاهش تکرار

مثال ذهنی تیکت: User (id) → Ticket (user_id) → Kommentar (ticket_id)

🌐 REST API و JSON

  • متدها: GET خواندن · POST ایجاد · PUT/PATCH به‌روزرسانی · DELETE حذف
  • کد وضعیت: 200 OK · 201 Created · 400 Bad Request · 401/403 · 404 · 500
  • JSON ساختار سبک برای تبادل داده
  • احراز هویت: Token / Basic / API-Key (هرگز در کد عمومی سخت‌کد نکن)

🔐 Informationssicherheit و DSGVO

  • Datenminimierung – فقط داده لازم
  • Least Privilege – حداقل دسترسی
  • رمزنگاری در انتقال (HTTPS)
  • لاگ دسترسی برای سیستم‌های حساس
  • داده شخصی = مسئولیت حقوقی (DSGVO)

📦 تحویل به مشتری

محصول بدون مستند ناقص است: چگونه صدا زده شود، چه فیلدی برمی‌گردد، خطاها، پیش‌نیازها، نسخه. Lehrplan صریحاً Dokumentation zur Handhabung را می‌خواهد (حتی به زبان خارجی).

✏️ تمرین‌های امتحانی

۱

سه منبع فروش (DB، CSV هفتگی، API فروشگاه) را از نظر ساختار، دسترسی و ریسک امنیتی جدول کن.

۲

ER برای User/Ticket/Kategorie/Kommentar + یک JOIN برای تیکت‌های باز یک کاربر.

۳

قرارداد API بنویس: GET /tickets → فیلدها و دو کد خطا.

۴

چرا CSV روزانه از سرور حسابداری را بدون HTTPS نباید روی اینترنت عمومی بفرستی؟

۵

راهنمای یک‌صفحه‌ای مشتری برای همان API (آلمانی یا انگلیسی).
